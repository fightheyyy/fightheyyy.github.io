Agentic Eval · Release Engineering

Barena： Agent Eval 的终点， 不是排行榜， 而是发布 CI

我真正想测的不是一个 Agent 抽象地有多强，而是改了模型、Prompt、Skill 或工具之后，这一版到底敢不敢发。

更新于 2026.07.28 约 10 分钟阅读

Barena 最开始其实绕了点路。我先想的是“怎么给 Agent 打分”，后来越做越觉得不对：开发者每天面对的并不是排行榜问题，而是一个很具体的工程问题——我刚改了 Prompt、换了模型、加了 Skill，这个版本能不能发布？

单元测试当然还要写，但它只能兜住确定性的那部分。真正的 Agent 行为还取决于模型选择了什么路径、有没有正确调用工具、文件到底写没写出来，以及同一个任务重跑几次会不会忽好忽坏。于是我把 Barena 收成了一个更明确的产品：测试真实 Agent，并把执行结果变成发布证据。

我最后只保留了三个入口

Barena 现在对外只有三个核心动作。它们不是三个彼此独立的产品，而是在回答发布前的三个不同问题。

命令 它问什么 什么时候用
barena explore 真实用户还会撞到什么边界？ 让 UserCat 多轮模拟用户，探索尚未写成 Case 的问题
barena replay 已经修好的能力有没有被改坏？ 用固定 Case 重放历史任务，并检查最终产物
barena compare Candidate 相比 baseline 到底改变了什么？ 在隔离条件下比较两个版本，形成发布结论

Explore 负责发现未知问题；一旦问题被复现，它就可以沉淀成 Replay Case；当下一版 Agent 出现时，再用 Compare 判断变化是提升、无效还是回归。这个闭环比“跑一次、给一个总分”更接近真实研发过程。 

Explore unknown behavior
        ↓
find a reproducible issue
        ↓
promote it to a Replay Case
        ↓
Compare baseline ↔ candidate
        ↓
cleared | held | rejected

被测 Agent 不应该被绑死在一个框架里

做到这里之后，另一个问题马上出现了：Claude Code、Codex、XiaoBaOS、OpenClaw 都有自己的命令、会话和 Trace。如果每接一个 Runtime 就重写一套评测，Barena 很快会变成 Adapter 大杂烩。

所以 Runtime 接入和评测逻辑必须分开。Barena 通过统一的 Runtime / Target Adapter 管理 session、turn、取消和工作目录；能导出原生 Trace 的 Runtime，统一走 OpenTelemetry / OTLP。Trace 负责解释过程，Artifact 与确定性 Verifier 负责检查结果。两边都保留来源，不会把进程边界观察伪装成 Runtime 内部轨迹。

为什么一定要有 baseline

我一开始也觉得 Compare 有点多余：Candidate 能把任务做完，不就说明它有效吗？真正跑过几轮之后才发现，绝对分数很容易骗人。

假设新 Skill 跑出了 100% 通过率，看起来很好。但如果不加载这个 Skill，原来的 Agent 也是 100%，那这次变更并没有证明任何增益。相反，如果 candidate 总体分数提高，却把一个原本稳定通过的关键 Case 做坏了，平均分也不应该替它开脱。

Compare 因此固定任务、Runtime、Role、工具和验证器，只改变要评估的候选项，并给两边创建独立 workspace 与 session。它不是严格的因果实验，但至少尽量把问题缩小到：除了这次变更，还有什么不同？

Agent 说“完成了”，不能算完成

这是做 Agent Eval 最容易踩的坑。Agent 可以非常自信地说“文件已经生成”，Reviewer 也可能觉得它的回答不错，但磁盘上根本没有目标文件。只让另一个模型评价它，最后很容易变成两个模型互相认可。

Barena 把证据拆成三层：最终回答记录 Agent 的声明；Trace 解释它走了什么路径；Artifact Verifier 直接检查文件、JSON 结构、内容和其他可观察状态。发布结果以 Verifier 为准，Reviewer 主要负责解释失败模式。

证据 能回答什么 不能替代什么
Final answer Agent 声称自己做了什么 真实结果已经存在
OTel Trace 调用、工具和阶段怎样发生 最终状态一定正确
Artifact Verifier 可观察结果是否满足断言 过程一定合理

我用 24 个公开任务真正跑了一遍

到这里，Barena 的方法听起来是成立的，但我不想只拿 fake fixture 证明自己的框架。所以我从 SkillsBench v1.1 的 8 个类别里各选了 3 个任务，用同一个 XiaoBaOS Agent 比较“不加载任务 Skill”和“加载任务 Skill”。

实验矩阵是 24 个任务、两个 arm、每边 3 次独立运行，一共 144 次 rollout。任务是否成功只看 SkillsBench 的确定性 Verifier，不采用 Agent 自述，也不拿 Reviewer 分数代替。

统计项 结果 为什么这样算
终态运行 144 / 144 所有计划运行都到达终态
Verifier-admitted 90 / 144 只有能证明 Verifier 实际执行的结果才准入
严格匹配 pair 36 对，覆盖 14 个任务 同一任务、同一 trial，两边证据都有效
匹配集通过率 38.9% → 55.6% 观察差值 +16.7 个百分点
完整任务门禁 2 cleared / 7 held / 0 rejected 只有 9 个任务拥有完整的 3×3 证据

这个结果没有海报上一个 “+16.7 pp” 那么简单。144 次运行里只有 90 次通过证据准入；其中 72 次组成了 36 个严格匹配 pair，另外 18 次因为另一边缺少有效对应项，不能进入配对比较。剩下 54 次是无效或没有评分的结果。

在 36 个匹配 pair 中，baseline 通过 14 次，candidate 通过 20 次；candidate-only pass 有 8 次，baseline-only pass 有 2 次。方向是正的，但 exact McNemar p = 0.109，再加上缺失可能不是随机发生，所以这次实验不能证明 candidate 在总体上显著更强。

这次实验验证的是评测方法，不是给 XiaoBaOS 发一张冠军证书。

Barena 能把完整运行、有效证据、可比较样本和发布结论分开；它也能在数据不够时返回 held，而不是为了讲故事把所有运行硬塞进同一个分母。

这次实验反过来改了 Barena

真数据最有价值的地方，是它会逼框架暴露偷懒的地方。跑完这 144 次之后，我给 Barena 补了几条更严格的规则：

  • “进程结束”不等于“结果有效”，Verifier 是否真正执行必须有独立证据。
  • baseline 和 candidate 必须按 task 与 trial 严格配对，不能用两个不同分母的总体通过率直接相减。
  • 证据不完整的任务留在审计索引中，但不能参与效果结论。
  • held 不是失败，它表示当前证据还不足以做发布决定。
  • 公开报告必须同时给出选择、准入规则、排除项和机器可读结果，不能只放一张漂亮图。

这也是我现在理解的 Release CI：它不保证永远做出正确决策，但必须保证每个决策都能追到真实任务、真实运行和明确的证据边界。

当前版本能做什么，不能做什么

Barena 现在已经是一个可运行的 v0.1，而不是只有架构图的概念项目。三个 CLI 入口都能进入真实执行引擎；XiaoBaOS Explore 已经跑通 UserCat、目标 Role、InspectorCat、ReviewerCat 和原生 OTLP Trace；Replay 与 Skill Compare 也有独立运行、Verifier、证据包和发布门。

但边界也要说清楚：

  • 当前深度适配的 Explore Runtime 是 XiaoBaOS；Claude Code、Codex 和 OpenClaw 的多轮 Explore Adapter 仍待完成。
  • 当前 compare 主要复用已经验证的 Skill baseline / candidate 引擎，最终的任意 RunSet 对比还在后续版本。
  • SkillsBench 实验早于现在的 OTLP Explore 路径，因此它验证的是配对准入、Verifier 和门禁方法，不是新 OTLP 模块的实验成绩。
  • 公开仓库保留结果、选择和可移植证据索引；原始 provider trajectory 没有全部公开。
  • 有限次 Replay 能发现 flakiness，但不能证明概率意义上的绝对稳定。

为什么我仍然觉得 Release CI 是 Agent Eval 的落点

Benchmark 很重要，它告诉我们一个模型或 Agent 在公共任务上大概处于什么位置。但真正进入研发流程之后，团队最终还是要回答更窄的问题：这次改动有没有提升？有没有回归？结果稳不稳定？证据够不够？

Barena 想把这些问题固定成每次发布都会执行的动作。Explore 去找未知边界，Replay 守住已经获得的能力，Compare 决定一个 candidate 是否值得进入下一步。Trace 解释发生了什么，Verifier 检查现实里到底完成了什么。

这个项目还很早，但它已经不再只是一个想法：三个产品入口、XiaoBaOS 深度适配、OTLP Trace、157 项自动化测试，以及一组 24 任务、144 次运行的公开实验都已经落地。接下来要做的不是再造一个排行榜，而是继续把 Agent 的每次行为变化变成可复现、可比较、可审计的发布证据。
