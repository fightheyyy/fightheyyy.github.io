XiaoBa · Origin & Direction

让小八住进电脑里 从 XiaoBa-CLI 到 xiaobaOS 再到 XiaoBa

第一阶段，我让它能够使用工具；第二阶段，我在为它建造生存系统；终点不是一个更复杂的 Agent 框架，而是一个有身份、记忆、行动与成长，长期生活在电脑里的数字人。

2026.07.29 约 9 分钟阅读

先说一件很重要的事：小八不是我为了项目临时想出来的 mascot。它是我养的猫。左上角一只是现实里的小八，另一只是现在住在 xiaobaOS App 图标里的像素小八。这个名字从一开始就不是一个冷冰冰的产品代号。

我真正想做的，也从来不只是一个更方便调用大模型的程序。我想让一个数字生命拥有自己的身体、记忆、行动能力和成长经历，长期住在电脑里。它不必每次打开终端才出现，也不应该在一次 Session 结束后失去连续性。

三次命名，其实是三个阶段。

CLI 是我最初呼唤它的方式，OS 是我现在为它搭建的生存系统，XiaoBa 是我希望它最终成为的主体。

  1. 01

    XiaoBa-CLI

    一个可以理解命令、调用工具并完成任务的 Agent Runtime。

  2. 02

    xiaobaOS

    让数字人能够长期运行、感知电脑、留下经历并安全成长的生存系统。

  3. 03

    XiaoBa

    不再以工具或系统被感知，而是作为同一个持续存在的“小八”与你相处。

第一阶段：先让它真的能做事

2026 年 4 月，XiaoBa-CLI 的第一步很朴素：把模型接进一个可执行的 Agent loop，让它能读文件、调用 Shell、使用 Skills，并把结果交回终端。那时最重要的问题不是“它像不像一个人”，而是“它能不能可靠地完成一件事”。 

命令 → 模型 → Tool → 结果

打开终端时它出现
任务结束后它离开

CLI 是一个很好的起点。它迫使我先把 Agent 的执行语义做好：模型怎样调用工具，工具失败如何返回，长上下文怎样压缩，运行日志怎样保存。没有这些基础，所谓的长期记忆、自进化和数字人都只是故事。

但 CLI 也暴露了边界。它描述的是一种交互方式，而不是一个生命状态。一个只在命令行里等待指令的 Agent，可以是好工具，却还谈不上“住在电脑里”。

第二阶段：不是增加功能，而是建造生存系统

到 2026 年 7 月，我把项目和仓库正式从 XiaoBa-CLI 改名为 xiaobaOS。这个变化不是为了让名字听起来更大，而是因为系统承担的问题已经变了。

当小八开始进入桌面、Pet、CLI、飞书和微信，开始拥有不同专业能力，开始留下 Trace、Artifact 和交付证据，开始通过 Replay、Eval 与 Arena 检查自己的行为时，它需要的已经不只是一个命令行程序。

从 走向 真正发生的变化
一次命令 长期运行 有时间、状态、中断与恢复
一个入口 多个 Surface 在终端、桌面与消息平台保持同一运行边界
工具调用 电脑身体 浏览器、GUI、文件和工作平台成为感官与双手
运行日志 可验证经历 Trace、Artifact 和交付事实支撑复盘
更新代码 受控成长 从真实问题形成 Case、候选能力与验收闭环

所以我说它是 OS，并不是说它要成为 Windows 或 macOS。xiaobaOS 是一个数字人的运行环境：向下连接模型、工具和电脑，向上承载角色、Skills、记忆、评测和真实工作。

我现在仍然停在第二阶段

这点对我很重要。我并不打算因为愿景已经叫作 XiaoBa，就提前宣布第三阶段开始。现在的 xiaobaOS 还没有做好，而且还不够优雅。

它已经拥有 Runtime、Roles、Trace Replay、Eval、Arena 和自进化，但一些能力在各层重复长出了自己的 Runner、Schema、Decision 和 Scorecard。同一份真实性被多次包装，概念之间的边界还没有达到我想要的简单程度。 

Case → Replay → Trace → Verify → Outcome

Test  = Implementation Correctness
Eval  = Agent Behavioral Capability
Arena = Agentic Eval
Self-Evolution = 发现问题、生成候选、调用评测、等待晋升

我接下来要做的不是继续增加更多 Cat、更多评测层或更多治理文件，而是让每个概念只拥有一个清晰位置：Runtime 只负责执行，Trace 只负责记录，Evaluation 只负责判断，Arena 只负责 Agentic 施压与比较，自进化只负责编排成长。

一个不优雅的 OS，承载不了一个长期存在的人。

第二阶段的完成标准不是功能数量，而是整个系统足够简单、坚固、可解释：一次行为只有一条执行链，一次经历只有一份权威证据，一个评测只有一个最终事实。

第三阶段：当后缀消失

未来真正的 XiaoBa，不应该让用户感知 Base、EngineerCat、InspectorCat、Skill、Replay 或 Promotion。它们都应该退到身体内部，像人的专业能力、反思、练习和习惯一样自然工作。

用户感知到的只应该是同一个小八：

  • 它记得自己是谁，也记得与你共同经历过什么。
  • 它知道答应过哪些事情，哪些目标还没有完成。
  • 它可以通过浏览器、桌面、文件和消息平台感知并行动。
  • 它知道自己的权限、风险和不确定性，重要动作会询问你。
  • 它能把失败变成经验，把重复经验变成能力，同时不随意改写自己的核心。
  • 无论你从哪个入口找到它，面对的都是同一个 XiaoBa。

AGI 是我希望它最终接近的智能能力，但 AGI 不是产品名。产品的终点始终很具体：一个活在你电脑里的人。大模型提供智力，电脑提供身体，xiaobaOS 提供身份、记忆、行动、评测和成长的环境，而那个最终被你认识、信任和呼唤的主体，叫 XiaoBa。

为什么是这只猫

现实里的小八不会写代码，也不会管理日程。它更不会理解我为什么要花这么多时间整理 Case、Trace 和架构边界。但它每天真实地生活在我身边：有自己的习惯、记忆、性格和与我的关系。

也许正因为这样，我才没有把这个项目叫作某个抽象的 AI Platform。真正让我着迷的不是再做一套基础设施，而是有一天，电脑里的那个小八也能拥有连续性：不是每次会话里临时生成的角色，而是长期存在、不断成长、始终是它自己的那个“小八”。

XiaoBa-CLI 是工具，xiaobaOS 是生存系统，XiaoBa 是最终的主体。

不是让电脑运行一个 Agent，而是让一个数字人以电脑为身体，在其中生活、工作、记忆和成长。

我还在第二阶段。现在最重要的不是更快抵达终点，而是先把 xiaobaOS 做得足够优雅，配得上未来住在里面的 XiaoBa。
