去年 4 月到今年 4 月，我在一家初创公司实习了大约一年。其中一项工作，是开发一个给企业用的轻量 Agent Harness。

它和 Coding Agent 的 Harness 不太一样。我们不需要先把一个复杂的软件开发环境搬进去，主要就是几块：IM 等交互入口、Context 管理、Session 管理、Tool Manager，以及可观测性。企业的工作流程写成 Skill，再把需要的知识和工具接上，让 Agent 能把任务跑起来。

具体业务就不展开了。我想讲的是，Harness 开发完之后，我在做什么。

对接企业，拆需求，看运行记录，找 Bad Case，放进回归集，把问题和上下文交给 Codex 或 Claude Code，改 Skill 或 Harness，再做端到端验收。验收没过，继续看 Trace，再来一轮。

这套流程里已经有 Agent 了，而且不止一个。但中间负责传递消息、整理材料、记住这次改动从哪来的人，还是我。

我当时的工作，其实就是一个人工的数据飞轮。

后来做 [OpenFlywheel](https://github.com/fightheyyy/OpenFlywheel)，我想接起来的就是这段工作。这个项目之前叫 CATENA，现在 CATENA 是里面的 Web 控制台。

## 为什么 Harness 跑起来之后，还需要一个飞轮

把一个企业需求做成 Skill，通常只是第一轮。

真实用户不会一直按我们预想的方式提问。知识会更新，工具会出错，前面的对话会影响后面的执行。同一个任务，演示时做对，换一个 Session 或换一种问法，结果可能就变了。

这些问题不一定要靠换模型解决。有时候需要改 Skill，有时候是 Context 没带全，有时候是工具返回值处理错了，也可能只是企业自己的知识过期了。

所以后面的工作会变成：从真实使用里找到问题，弄清楚应该改哪里，再证明这次修改确实有用。

如果每一步都靠人临时整理，经验很容易留在聊天记录里。这次找到了一条失败 Trace，下次又得重新解释背景；今天让 Coding Agent 修好了一个问题，过几天却说不清它有没有影响以前正常的任务。

**我希望一次排查结束后，留下的不只是一个改动，还有能复现它的 Case、验收标准，以及这次修改的对照结果。** 下一轮遇到类似问题，可以接着往下做。

从这个角度看，企业 Agent 数据飞轮大致就三块：

1. 收集运行记录，从里面找出值得处理的问题。
2. 把问题、知识和执行环境交给受管理的 Agent，生成候选改动。
3. 对照旧版本验收，决定采用、拒绝，或者继续调查。

## 第一块：收集 Trace，但先别急着让模型看所有东西

飞轮的输入，首先得来自真实运行。

我会用 OpenTelemetry 和 OTLP 把运行记录接进来。至少要能关联到哪一个 Agent、哪一次运行、用了哪个版本，以及相关的工具调用、错误和结果。否则修完以后，连后续 Trace 属于新配置还是旧配置都分不清。

不过，接上可观测性不代表已经知道问题出在哪里。这里我会把两类工作分开。

**一类是很明确的异常信号。** 比如命令不存在、工具返回非零退出码、反复重试、执行异常终止。这些适合先用规则找、按指纹聚合，没有必要每条都调用一次模型。

OpenFlywheel 目前的 Signals 就在做这件事：用确定性规则找重复失败，检测本身不消耗模型调用。但一个工具报错，只能说明这里值得看。Agent 后面可能换了工具并完成任务，不能直接把整次运行判成失败。

**另一类是业务结果不好。** 这通常更难。

比如，Agent 成功读了知识库，也交付了文档，所有工具都返回成功，但它漏掉了企业在意的一条约束。Trace 里的错误码帮不了我们。要判断这份结果能不能用，需要懂业务的人看，也需要知道当时的任务要求是什么。

LLM 可以先筛出一些可疑结果，把相关证据整理出来，减少专家翻日志的时间。但筛选结论仍然是待确认的问题，不能直接变成企业认可的质量标准。

我觉得这里最容易走偏的地方，是把异常检测、归因和业务验收都叫作“分析 Trace”。它们需要的证据不同，能自动化的程度也不同。

前面可以尽量便宜地筛，后面再把模型和专家的时间花在值得看的问题上。

## 第二块：把我交给 Coding Agent 的那些材料，变成系统里的任务

我以前手动做这件事时，其实已经有一套很朴素的流程：找几条相关 Trace，把企业的要求补上，指出可修改的 Skill 或 Harness，再交给 Codex、Claude Code 去处理。

所以我会想，如果一家公司的 Token 真能无限用，能不能让 Managed Coding Agent 加上一些 Skill 和企业知识，把发现问题、调查原因、尝试修改这部分也接过去？

至少很大一部分整理和执行工作，可以往这个方向做。但即使不考虑 Token 成本，也要先把任务交代清楚：它能看什么，能改哪里，做到什么算完成。

“看看最近这些 Trace，优化一下”给的信息太少。模型不知道哪些错误最重要，不知道企业已经确认了哪些要求，也不知道哪一份配置才是当前版本。让它自己猜，最后往往还是要人补上下文。

因此我希望交给改进 Agent 的是一份具体任务：问题来自哪些 Trace，复现 Case 是什么，当前版本是什么，可以修改哪些文件，以及哪些旧能力必须保持。

这也是我会考虑 **Managed Agent + OpenSandbox** 的原因。

Managed Agent 这一层负责让任务可以持续执行：Session 要保存，Worker 要能认领任务，执行中断后要知道能否恢复，模型、Skill 和工具权限也要明确。OpenSandbox 则给需要执行命令的工具提供隔离环境。两层承担的事情不同，不能只套一个沙箱就认为 Agent 已经可以被管理了。

最初考虑这部分时，我参考了 OMA。按[当前实现](https://github.com/fightheyyy/OpenFlywheel/blob/c068fff/docs/ARCHITECTURE.md)，OpenFlywheel 借鉴的是它的 Worker、Session 和任务认领边界，运行时直接使用已发布的 DSH 包，没有导入 OMA 源码。OpenSandbox 在启用的 Shell 工具首次执行时才创建，任务执行后清理；持久 Session 和模型凭证留在沙箱外。

这里还有一个很实际的边界：Trace 是被分析的数据，里面可能包含用户输入、工具输出，甚至看起来像指令的文本。调查 Agent 不能因为读到一段话，就获得新的工具权限。

落到企业里，也是同样的问题。一家企业的 Trace、知识、凭证和候选改动要能对得上，不能因为大家都用了同一个 Worker Pool，就混进另一家企业的任务。

我想省掉的是人在系统之间搬材料的工作。企业允许改什么、什么结果算合格，仍然得先有人定义。

## 第三块：改完以后，谁来证明它更好了

Coding Agent 给出一个修改，并不难。难的是它为什么值得被采用。

如果改进 Agent 看完 Trace，修改 Skill，最后再由它自己读一遍并评价“效果更好了”，我不太会放心。它可能只是把眼前这一条 Case 做对了，也可能加了一大段规则，让其他任务更慢、更贵，或者把原本正常的行为改坏了。

所以第三块，我会用 Harbor 做新旧版本的对照验收。

这里说的 A/B，先指**同一组任务下 Baseline 和 Candidate 的成对评测**，不等于已经把两个版本分流给真实企业用户。

旧配置和候选配置要在可比较的环境里跑，尽量排除上一次运行留下的文件、安装状态和其他副作用。判断依据也要落到任务结果上：该生成的文件有没有生成，内容是否符合要求，命令是否真的成功，原来的回归 Case 有没有退化。业务质量如果还只能靠专家判断，就把专家审阅留在验收里。

这里还有一件事得提前做：固定验收用的 Case。不能候选做不出来，就顺手把验收标准一起改了。

当前 OpenFlywheel 会区分训练 Case、独立验证 Case 和历史回归 Case。优化器根据训练证据找候选，候选冻结后，再交给 Harbor 在新鲜容器中做独立对照。具体流程和边界放在[闭环说明](https://github.com/fightheyyy/OpenFlywheel/blob/c068fff/docs/EVOLVE.md)里。

它目前能自动草拟复现的范围还很窄，主要是缺失 `rg` 这一类问题。其他故障仍需要人登记、审阅 Harbor Case。这个限制要讲清楚：从一条真实 Trace 生成一个能复现、能裁决的任务，本身就是工作，不能拿一个总能通过的模板把这个环节糊过去。

最后还得看成本。质量好一些，多用了多少 Token，多花了多久，企业愿不愿意接受？这些取舍需要摆出来。Token 多不代表一定差，Token 少也不代表一定好。

## 验收通过之后，还要能应用，也要能退回去

我以前人工跑这套流程时，验收之后还有一步：把确认过的修改放进实际使用的版本里。

所以报告里显示 Candidate 通过，还没有走完整个闭环。采用的是哪份配置、改了哪些文件、之后的运行用没用上它，都要能查到。

OpenFlywheel 当前保留人工 Adopt。网页上的采用决定授权交付，本机 CLI 再负责把配置应用到目录，或者走 PR。应用前保留旧内容，需要时可以回滚。后续 Trace 也会关联活动版本，帮助继续观察。

如果同一个故障指纹在采用后再次出现，系统会标记 `REGRESSED`。我会把它看作“这个问题又来了，需要调查”的提示，不能仅凭先后顺序，就证明一定是新版本造成的。

同样，回归集里没有退化，只能说明这批已确认的任务没有观测到退化。它不能替未来所有企业需求作保证。

飞轮要继续转，就得把上线之后的结果再收回来。否则最后留下的还是一份验收报告。

## 通用部分可以复用，企业自己的那段绕不过去

按这个思路，大块的基础设施其实都有不错的开源项目可以复用：OpenTelemetry 做运行记录接入，Managed Agent 的设计和现成 Agent Runtime 承担调查、改进任务，OpenSandbox 隔离工具执行，Harbor 做评测环境和对照运行。

OpenFlywheel 要补的是这些步骤之间的衔接。一个问题从哪里来，谁调查过，复现 Case 是否确认，候选依据什么生成，评测的是哪一个版本，最后谁采用了它。这些信息不能每次都靠人从聊天记录里拼。

但把它们接起来以后，还不能直接复制出任意一家企业的飞轮。

企业得提供自己的知识、工具和权限，得有人把“这次结果不对”说成可检查的要求，也得持续整理真正有价值的回归 Case。合同审阅、知识问答和数据分析，不会因为用了同一个 Harbor，就拥有同一套 Verifier。

当前项目验证的是这条工程闭环，以及其中有限范围的受控复现。我不会把它写成已经替企业完成了所有业务归因和自动发版。

对我来说，做这个项目的出发点一直很具体：当我已经在反复做“看 Trace、找问题、交给 Coding Agent、验收”这些工作时，就应该让系统接住能固定下来的部分。人的时间留给需要业务判断的地方，排查出来的经验则留下来，进入下一轮运行。
