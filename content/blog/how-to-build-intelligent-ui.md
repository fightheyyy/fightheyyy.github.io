今年 8 月，我花了一段时间研究怎么给 Agent 做 UI。当时做的是 LexVoice × SuperWebApp：用户可以通过语音、摄像头、触控发起请求，Agent 调工具，前端再把结果放到对应的画布里。

有些结果适合直接播报，比如时间。有些需要留在屏幕上，比如提醒列表。有些还需要用户继续操作，比如选商品、改规格、确认订单。

如果全部塞进聊天气泡里，用户就要不断用语言描述本来点一下就能完成的操作。但如果每次都让模型生成一整个页面，提醒列表、商品详情这种已经知道该怎么展示的东西，又要重新生成一遍。

我最后把需求拆成三类，分别看待：

| 要展示什么 | 我会用什么 | 前端负责什么 |
| --- | --- | --- |
| 已知工具返回的业务数据 | MCP Apps | 加载对应 App，把结果交给已有界面 |
| 模型临时整理、组合出来的内容 | A2UI | 用约定好的组件渲染内容结构 |
| Agent 和 Subagent 正在执行的过程 | AG-UI | 接收事件，更新运行状态和阶段结果 |

这三类接起来，已经能覆盖我当时想做的大部分 Intelligent UI。关键是先分清楚：这一次需要的是一个结果界面、一份动态内容，还是一个正在运行的任务。

图里上半部分是一条共同链路：用户输入，LexVoice Agent 理解意图、编排工具，工具返回结果。结果可以交给语音播报，也可以交给 SuperWebApp 展示。

下面的今日、探索、记忆等画布，则是不同的界面容器。它们不是一个个 Tool，也不一定和 MCP App 一一对应。

比如今日画布里的 Today App，可以承接天气、时间和提醒相关的多个工具。探索画布里又可以同时容纳 Search App 和 VQA App。工具怎样拆，和用户看到几个界面，是两件事。

这个区分很有用。否则后端每新增一个 Tool，前端就多一个窗口，产品很快会变成工具调试面板。

## 第一类：已知工具的结果，交给 MCP App

像提醒、日程、商品详情这类场景，数据和操作通常都比较明确。

提醒有时间、内容和状态，用户可能要修改、暂停或取消。没有必要让模型每次重新决定暂停按钮应该放在哪里，或者把提醒对象改写成一段文字，再让前端从文字里猜字段。

这里我会先写好 App，把 Tool Result 交给它。模型负责选择工具和参数，界面负责展示和操作。

**固定的是数据契约和交互，不是每次返回的内容。** 同一个提醒 App，可以显示不同日期、不同数量的提醒，也可以随着工具结果更新。

在 MCP Apps 里，工具声明关联的 UI 资源，例如 `_meta.ui.resourceUri` 指向一个 `ui://` 地址。支持这一扩展的 Host 读取资源，在沙箱 iframe 中加载界面，再通过桥接通信把工具结果传进去。App 的交互也经由 Host 与工具侧衔接。[MCP Apps 官方说明](https://modelcontextprotocol.io/extensions/apps/overview)

当时图里对应的就是这一段：

```text
Tool 与 UI 资源绑定
        ↓
Host 加载 ui:// 资源
        ↓
AppBridge ↔ Sandbox iframe
        ↓
App 接收 Tool Result，展示数据与操作
```

我比较在意的是，同一份结果要同时支撑界面和播报。语音可以做摘要，界面可以展示详情，但不应该各自生成一套业务事实。比如提醒到底创建成功没有，应当来自工具执行结果，而不是 UI 先显示一个成功动画，Agent 又说一句“已经好了”。

另外，iframe 只是承载和隔离界面的方式。按钮点下去以后能做什么，仍然取决于 Host 开放的能力和服务端权限。把页面放进 iframe，并没有替业务接口完成授权。

## 第二类：模型需要重新组织内容，用 A2UI

不是所有任务，都能提前找到一张合适的业务卡片。

比如用户让 Agent 搜集几份材料，整理成对比，再列出待确认事项。数据可能来自多个工具，最后要怎么分组、哪些信息值得放在一起，要等模型整理以后才知道。

如果继续给每种组合写一个专用 App，会出现很多只用一次的界面。但让模型随便生成 HTML 和脚本，我也不想把整套前端交出去。

这类情况，我会用 A2UI 描述内容结构：这里是一组卡片，那里是一个列表，下面是几个可以继续操作的控件。客户端用自己的组件把它画出来。

A2UI 的基本思路是由 Agent 输出声明式 UI 描述，客户端通过组件目录和 Renderer 完成展示。这里我采用的是受约束的组件组合：模型决定内容怎么组织，前端掌握实际组件、样式和可用动作。[A2UI 工作方式](https://a2ui.org/concepts/overview/)

我说“没有固定 Tool Result”，更准确地说，是**没有一份可以直接套进专用业务界面的结果结构**。它的数据仍然可能来自工具，也可能通过一个工具提交 UI 描述。区别在于，展示结构需要模型在这次任务里整理。

图里的 Generic Canvas，就是给这类内容留的位置：

```text
模型整理数据与展示结构
        ↓
spawn_widget
        ↓
A2UI Envelope
        ↓
A2UI Renderer
```

这里的 `spawn_widget` 是当时方案里的工具名，不是 A2UI 协议要求所有人都实现的接口。

## MCP App 做外壳，A2UI 做里面的内容

这也是整张图里我觉得最值得保留的一点。

Generic Canvas 本身仍然是一个 MCP App。Host 认识的是这个 App，通过原来的加载和桥接方式把它放进 iframe。App 内部再运行 A2UI Renderer，接收模型整理出来的内容。

因此，外层不用因为内容变了，就再实现一套窗口、生命周期和工具通信。里面的卡片、列表和控件可以按这次任务变化。

```text
SuperWebApp / MCP Apps Host
└─ 通用 MCP App：负责接入与交互桥接
   └─ A2UI Renderer：负责动态内容
      └─ 客户端允许的组件与动作
```

这是一种组合方式，并不意味着 A2UI 必须放在 iframe 里。在我当时的设计中，既然前端已经需要承载其他 MCP App，把通用内容也放进同一套容器更直接。现在 A2UI 的官方文档里也有[在 MCP App 内嵌入 Renderer 的集成方式](https://a2ui.org/guides/a2ui-in-mcp-apps/)。

前端需要约定清楚可用组件和动作。模型输出了一个不支持的组件，应该报告或降级；模型生成了一个“取消”按钮，也要知道它取消的是哪个对象、调用哪一个受支持的动作。只有外观，没有动作契约，用户点下去还是没法完成事情。

## 第三类：任务还没结束，用 AG-UI 展示过程

前面两类主要在回答“结果怎么显示”。但像 S2 Agent Harness 这样的长程任务，或者一个主 Agent 启动了几个 Subagent，用户往往不能等到最后才看到界面。

他需要知道：任务有没有开始，现在做到哪一步，哪个子任务结束了，哪个遇到错误，还有没有需要自己补充的信息。

这部分我会用 AG-UI，把运行过程作为事件送到前端。它提供运行生命周期、消息、工具调用和状态更新等事件；前端据此更新任务视图，不必只依赖最后一段自然语言回复。[AG-UI 事件说明](https://docs.ag-ui.com/concepts/events)

比如一个需要检索、整理和校验的任务，界面可以分别展示这些阶段。Subagent 产生的事件和阶段产物，需要关联到对应的执行记录，避免几条任务同时跑时，所有进度都挤进同一个“处理中”。

但页面上的状态必须有执行依据。Agent 说“我准备检查”，不等于检查已经完成；工具参数发完了，也不等于工具成功。前端应该用实际执行事件更新状态，结果界面再展示已经拿到的产物。

AG-UI 本身不会替 Harness 调度 Subagent，也不会凭空提供持久任务、取消或恢复能力。后端有这些能力，前端才有东西可以展示和操作。事件协议解决的是两边怎样沟通。

图里没有展开这部分，所以我会把它看作同一个产品里的另一条链路：任务事件更新外层过程视图，产出的固定结果进入 MCP App，需要临时组织的内容则进入 A2UI Surface。

## 放到一次任务里看

假设用户说：“帮我查一下今天的安排，再找几份材料做个对比。”

今天的安排有现成的数据结构，可以交给日程 App。查资料可能花一段时间，可以用 AG-UI 更新检索、整理等阶段状态。最后的对比结构需要根据找到的材料组织，可以用 A2UI 在通用 App 里展示。

三种形式可以同时出现在一个页面里：左边是任务状态，中间是模型整理的对比，旁边是能继续操作的日程卡片。不用强迫它们都变成聊天消息，也不用要求每一块都由模型重新生成。

对用户来说，更重要的是它们能接着用。改了一个提醒，列表要更新；任务失败，要知道失败在哪；对比里的一个结论，最好能回到材料来源。多渲染一张卡片本身解决不了这些问题。

## 我会先把这三类接好

现在回头看，做 Intelligent UI 时，我会先问：哪些交互已经很明确，哪些内容确实需要模型临时组织，哪些工作需要把执行过程展示出来。

明确的业务交互，用现成 App 做扎实。动态内容，让模型在约定的组件里组合。长程任务，把真实事件接到前端。这三类之间再统一对象标识、结果来源和动作回传。

当时研究完以后，我对“智能界面”的期待反而具体了很多：用户说一句话后，Agent 能把需要看的内容和需要做的操作带到面前；任务没做完时，用户也能知道它现在处于什么状态。

用 MCP Apps、A2UI 和 AG-UI 把这些连接好，已经能做出一套效果不错的 UI。剩下的，还是每个业务自己的交互细节。
