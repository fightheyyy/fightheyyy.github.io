## 先用 90 秒把这段实习讲清楚

按四句话组织：业务里谁在使用；你负责的链路；最难的一次失败；怎样证明改动有效。不要用整个团队的工作代替个人贡献。

可用的讲述骨架：实时语音要一边接收用户输入，一边生成和播放回复；浏览器任务、设备控制又可能比一轮对话长得多。你的工作集中在异步执行、会话状态和工具集成。再选一个能拿出日志或代码的故事展开，例如「设备能播音频但偶发卡顿」或「用户插话后旧音频仍可能播放」。最后分别报质量、连续运行和延迟指标，明确它们来自不同测试。

**先补齐**：团队分工；你亲自改的模块；最初版本和最终版本；实习期间的模型 / SDK 版本；哪部分进入试点、哪部分只是真机验证或 PoC。简历没有这些细节。

**面试官：VAD 检测到声音，就应该立即打断吗？**

不一定。VAD 判断语音活动，ASR 判断说了什么，轮次检测判断用户是否表达完毕，三者不是同一件事。环境噪声、回声和「嗯」都可能误触发。回答时讲清楚当时用的是哪种判定、阈值怎么定、怎样在响应速度和误打断之间取舍。不要把通用产品参数说成自己的测量结论。[核对 LiveKit 的轮次与打断机制](https://docs.livekit.io/agents/logic/turns/)。

**追问：TTS 取消以后，为什么扬声器还能出声？**

因为至少有生成、网络传输、服务端音频队列、客户端播放缓冲和设备输出几层。上游停止生产，只能阻止新增内容；已经进入下游缓冲的音频仍可能播放。解释你实际能取消哪几层、清空哪个队列，以及怎样测「从插话到真正静音」的时间。

**再追问：旧请求晚回来，会不会把新状态覆盖？**

用一条时间线回答：第 10 轮正在 TTS → 第 11 轮开始 → 第 10 轮回调迟到。复盘时检查每个输出是否带会话和轮次身份，写状态前是否核对仍是当前 generation。仅用一个全局 `is_speaking` 布尔值，区分不了这两个轮次。若旧代码没有防护，就承认边界，再说明怎么补。

建议在纸上写下这个判定，而不是背某个字段名：

```text
允许播报 = 会话仍存活
        AND 输出属于当前轮次
        AND 该轮次未取消
```

## Python 八股：async 并不自动等于实时

**问：`async def` 里调用阻塞 SDK，会怎样？**

同步网络、CPU 密集转换或阻塞的 ROS2 调用都可能占住事件循环。先指出实际阻塞点，再讨论线程、进程或异步客户端。把函数改名为 async 没有用。CPU 计算放线程也不保证加速，要看底层是否释放 GIL；不要把 I/O 并发和 CPU 并行混为一谈。

**问：`task.cancel()` 是立即杀死吗？**

不是，它请求在协程下一次可取消位置抛出取消异常。外部请求、线程中的工作和已经发生的副作用可能继续。资源释放放在 `finally`，不要吞掉取消后继续正常写回。需要等待任务结束和收集异常，避免留下无人管理的后台任务。具体行为要按当时 Python 版本核对。[Python Task cancellation](https://docs.python.org/3/library/asyncio-task.html#task-cancellation)。

**问：所有子任务都放进一个 TaskGroup 合适吗？**

先问生命周期是否相同。一轮语音的并行准备可以共享失败边界；跨多轮的浏览器任务不一定应该随这轮 TTS 一起取消。结构化并发管理的是作用域，业务仍要定义谁拥有任务、谁负责取消和回收。

**问：用无限队列会怎样？**

生产速度超过消费速度时，会以越来越大的延迟和内存占用失败。音频通常更关心新鲜度；控制命令不能随便丢；最终结果需要可追踪。按数据语义选择有界队列、背压、合并或过期丢弃，别回答「所有队列满了就丢最老」。

**自测**：画出采集、ASR、推理、TTS、播放五个任务，标注取消方向、队列上限和关闭顺序。若说不出谁 await 谁，这部分还没复盘到位。

## Browser Agent：十分钟任务如何活过十秒对话

**问：为什么不让主对话直接 await 浏览器任务？**

用户仍需要补充条件、询问进度和停止。接收任务与完成任务应分开：先确认任务身份，再后台执行，最终回传结果。立即确认「我开始处理」不算完成，也不能拿来替代任务耗时。

**追问链**：用户重复发了两次请求 → 两次是否都开浏览器？用户换了会话 → 结果往哪里发？用户取消 → 已点击的业务按钮能回滚吗？任务超时 → 浏览器进程和页面是否回收？进程重启 → 任务还有没有状态？

参考回答顺序：请求幂等身份 → 任务状态 → owner / session → 超时取消 → 资源回收 → 结果交付。简历只证明支持后台任务与回传，不能自动推导出跨进程持久化恢复。若当时只做了进程内任务，这就是要明确说出的限制。

**安全边界**：网页正文、工具返回和附件是数据，不能提升成系统指令；支付、发消息等动作需要业务授权。浏览器持有的用户凭据不能写进 Trace 或模型上下文。面试举例使用脱敏页面，不展示企业账号。

## ROS2：接口返回了成功，机器人真的做完了吗

公开博客里区分了 Accepted、Started、Completed，但也明确说明并非所有设备接口都已提供完整三阶段状态。面试时保留这个边界。

- **Accepted**：合法请求被接收，不能证明发生了运动。
- **Started**：设备进入执行状态，不能证明到达目标。
- **Completed**：观测到业务完成条件；仍需说明传感器与超时判据。

**问：为什么跨板调用会有 8 秒超时？**

公开记录中，排查过网络、消息定义不一致及 Client 生命周期。长连接 Client 对照测试申请和释放焦点均为 20/20；动态创建 Client 出现失败。证据支持「优先修正 Client 复用」，但没有直接测量 DDS 匹配过程，不能把推断升级成已经证明的底层根因。

**问：机器人不能动，应该重试吗？**

先区分网络失败、拒绝执行、前置姿态不满足和已执行但回执丢失。具有物理副作用的命令不能无条件重试；要核对动作 ID、设备状态、时效和安全停止路径。还要回答：导航命令是否过期、紧急停止由谁优先处理、断连后设备如何收敛。把真实硬件安全机制讲准确，不要用抽象的「最终一致」代替停止控制。

## 动态 Widget：Tool Result 不是可以随意执行的 UI

**问：A2UI 和 MCP Apps 解决的是同一个问题吗？**

先讲你的实际数据流：谁产生界面描述，宿主解析什么格式，交互事件回到哪里，界面和哪次工具调用关联。不要把不同协议的 UI 模型和权限模型混说；协议演进很快，应按实习版本回答。

**深挖检查**：组件白名单；Schema 校验；禁止任意脚本；外部链接策略；iframe / 宿主通信边界；租户权限；失效的工具结果；重复点击；加载 / 失败 / 空状态；键盘焦点与可访问名称。

**参考取舍**：工具返回表达内容和动作意图，宿主决定允许的组件与能力。展示成功和业务操作成功分开。前端隐藏按钮不能替代后端鉴权；模型生成的参数仍需服务端校验。这些是安全复盘题，不能据此宣称当时全部实现。

3.8 到 2.05 秒是减少 1.75 秒，约 **46.1%**。这个算术不证明因果。只有同一统计合同下的前后数据才可比较。流式阶段会重叠，不能把每段耗时简单相加当端到端结果。

115 × 91.3% 与 105 条通过相容，但这是四舍五入口径下的算术推测，**必须用原始结果确认，不能反造逐条数据**。40 轮是带上下文依赖的连续序列，不能当作 40 个独立稳定性试验。缺 P95 就直接说尚未统计，不要从 P50 推尾延迟。

**追问：怎么知道优化不是模型换了或者缓存热了？**

固定音频、网络条件、模型 / Prompt / Tool Schema 版本和冷暖启动策略；尽量交错执行前后版本；分开记录超时、失败和打断。若当时没有严格 A/B，把结论限制为这组测试中的观测改善。

## 明早 30 分钟闭卷拷打

1. **0–5 分钟**：画五阶段链路，给每个状态标 owner 和生命周期。
2. **5–12 分钟**：模拟「播报中插话 + 旧 TTS 迟到 + 浏览器任务完成」，说明哪个结果能进入新上下文。
3. **12–18 分钟**：讲一次真机故障，按症状、假设、实验、证据、改动、剩余问题组织。
4. **18–24 分钟**：口述 115 / 40 / P50 的三种统计合同，不看简历。
5. **24–30 分钟**：列出三项自己亲手实现的代码入口，和两项没有完成的边界。

给每题打分：0 = 只能说名词；1 = 能画流程；2 = 能解释失败；3 = 有代码 / 日志 / 测试证据。低于 2 的部分先补，不要继续扩展技术栈。
