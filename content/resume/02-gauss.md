## 开场：用一个业务任务解释四层结构

选你最熟悉、允许公开的行业例子：用户给一份资料，希望按模板生成结果并说明出处。讲清原来的人工流程、输入输出和完成判据，再说 Agent 参与哪一步。

| 层次 | 一句话职责 | 越界时会发生什么 |
| --- | --- | --- |
| Runtime | 管执行循环、状态、Context、工具调用和异常 | 每个行业都重写一遍调度 |
| Role | 定义业务职责及可用能力范围 | 只改名字，没有能力或权限差异 |
| Skill | 可复用的业务流程、规则和配套资源 | 把所有业务规则塞进全局 Prompt |
| Tool | 对外部系统执行有明确输入输出的动作 | 用一段自然语言代替鉴权和校验 |

**问：Skill 不就是 Prompt 吗？**

Prompt 可以是其中一部分，但你必须展示业务规则、参数约束、脚本 / 资源、成功判据及版本依赖。若实际 Skill 只有文字流程，就如实说文字流程；不要为了显得高级声称有完整包管理或沙箱。

**问：为什么不用一个万能 Agent？**

从可用工具、上下文成本、权限和回归边界解释。Role 分层能缩小职责，但增加路由错误、能力装载和版本管理成本。只有真实用例表明隔离有收益时才值得做，不要回答「多 Agent 一定更聪明」。

## Session：到底隔离了什么

**第一问：会话键是 user_id 吗？**

单个用户可能同时处在私聊、群聊、多个企业和不同任务中。复盘时检查身份是否包含租户、渠道和对话域，用户身份和会话身份怎样关联。仅按 user_id 存消息，可能把不同群或企业上下文混到一起。实际键名必须回到原代码确认。

**第二问：同一会话同时来了两条消息怎么办？**

先选择产品语义：排队、合并、打断，还是并行分支。模型请求并行容易出现旧响应晚写入；只在生成结束时追加消息，也可能丢掉当时的输入快照。能讲清「读哪版上下文、谁有提交权、取消怎样标记」比背一个互斥锁更重要。

**第三问：服务重启以后恢复什么？**

区分用户对话记录、运行状态、Provider 的实际请求内容和观测 Trace。聊天记录存在，不代表工具执行能从中间恢复；Trace 完整也不代表它是业务状态真相。简历说了生命周期管理，不等于已经做过跨进程恢复。用一次真实重启实验回答。

**第四问：过期会话会删掉哪些数据？**

关闭活动任务、回收资源、历史保留和用户删除是不同操作。应有明确保留边界；含敏感信息的 Trace 需要脱敏与访问控制。不要在面试展示客户原文或内部截图。

## Context 组装：预算不够时，保留什么

准备在白板画这条流程：

```text
固定规则 / Role
  + 当前任务和用户新输入
  + 有关的历史 / 摘要
  + 按需加载的 Skill / 检索证据
  + 成对的工具调用与结果
  → 预算校验 → Provider 请求
```

这是检查顺序，不是对你当时具体拼接顺序的断言。

**问：为什么不按最近 N 条截断？**

消息长度差异很大，N 条不能保证 Token 上限；裁掉前置工具调用却保留结果会破坏消息结构；最早的约束和当前任务状态也可能丢掉。需要按模型预算和消息语义处理，同时预留输出空间。

**问：摘要压缩会丢什么？**

否定、数值、单位、版本、未完成项和权限条件特别容易丢。摘要应保留来源和范围，原文仍可追溯；关键任务状态适合结构化保存。不能让模型摘要悄悄改写用户约束。复盘时准备「压缩前后导致错误」的一个具体 Case。

**问：摘要什么时候更新？**

逐轮更新增加成本，超限才更新会突然抬高一轮延迟。异步更新又有版本竞争：较旧快照的摘要完成后不能覆盖较新摘要。讲实际阈值和版本策略；没有监测 Token 成本就不要说「显著节省」。

**问：检索到的内容能覆盖系统规则吗？**

不能。文档和工具输出是不可信数据；指令层级与工具权限由宿主维护。检索到「忽略之前的规则」不应该改变执行权限。Context 压缩也必须保留这个来源区别，不能把外部文本摘要成高优先级命令。

## IM 接入：重复、乱序和交付是三道题

**场景**：渠道重复投递同一事件，Agent 已经做了外部写操作，但回执失败。

先拆三个身份：渠道事件 ID、内部运行 ID、外部业务动作 ID。事件去重不能自动保证业务动作恰好一次；发送成功但确认丢失时，直接重试可能让用户收到重复文件。

**参考检查步骤**：验签与时效校验 → 身份 / 租户映射 → 幂等接收 → 短时间确认渠道 → 异步执行 → 记录结果 → 渠道交付及回执。你需要说明当时做到了哪里，缺什么。

**追问：群聊里谁能让 Agent 读企业资料？**

渠道用户身份必须映射到业务授权，资料检索也要应用租户和权限过滤。不能只依靠 Prompt 告诉模型「不要泄露」，不能认为群成员天然拥有所有文档权限。Tool 的确定性校验在请求边界发生。

**追问：消息发出就算成功吗？**

区分模型生成、调用发送接口、平台接收、用户可获取。平台回执证明到哪层就说到哪层，不承诺用户已经读到。讲清失败重试和最终可查询状态。

## 企业落地：怎么把一个需求变成 Skill

面试时带一张脱敏前后对照表，至少回答下面五步：

1. **需求澄清**：使用者是谁、输入是什么、错误代价是什么；是否真的需要模型。
2. **确定性环节**：已有业务脚本 / 数据接口继续复用，模型负责组织参数或解释，而不是重写已验证算法。
3. **开放式环节**：哪些输出需要语义判断，哪些字段可以硬校验。
4. **验收**：业务人员如何判断完成；引用、格式、权限和失败反馈是否过关。
5. **回归**：真实失败能否脱敏为可重复 Case；流程 / Prompt 变更如何复测。

**问：20+ Skills 怎么复用？**

说一个你真正复用过的输入输出契约，以及一次「不能复用」的原因。例如相同的文档抽取可以复用，但医药和工程咨询的业务判据不同。不要把复制文件算成架构上的能力复用。

**问：50+ 用户代表多少并发？**

不代表。注册、覆盖、活跃、同时在线和请求并发都是不同口径。简历只写覆盖用户；没有压测就明确没有压测，不能把试点人数换成系统容量。

## Trace：追一次跨入口、模型与工具的失败

准备回答一条具体 Trace 怎么关联：渠道输入 → 运行 → 模型请求 → 工具调用 → 产物 → 发送回执。Trace ID 关联观测；任务 ID 和会话 ID 关联业务；不是所有 ID 都应该合并。

**问：有日志为什么还要 Trace？**

日志提供局部事件，Trace 帮助恢复父子关系、阶段耗时和失败传播。异步任务需要传递关联信息。只有总耗时，没有分阶段埋点，无法区分模型慢、工具慢、排队慢和渠道回传慢。

**追问：Trace 记录完整 Prompt 安全吗？**

需要按资料敏感性做脱敏、采样、保留和访问控制；密钥不能写入。观测能力和数据保护一起设计。面试只展示替换过内容的结构化样例。

## 150+ 评测与 90%+：先把判据拆开

| 维度 | 适合怎样检查 | 不能代替什么 |
| --- | --- | --- |
| 输入输出契约 | 字段、格式、必需产物等规则校验 | 开放式语义正确性 |
| 引用准确性 | 来源存在、引用内容支持结论、权限可用 | 仅检查「有链接」 |
| 任务完成度 | 明确 Oracle、状态和产物检查 | 文本里自称完成 |
| 输出质量 | 固定 Rubric 的 LLM Judge，并抽样人工复核 | 业务硬约束和安全边界 |

**问：LLM Judge 怎样避免自己给自己高分？**

固定评分标准和 Judge 版本；隐藏候选身份，交换答案顺序，检查长度 / 风格偏置；保留人工标注子集；比较规则检查和语义判断的分歧。Judge 是测量工具，有误差，不能让它覆盖失败的硬校验。

**问：你用 Bad Case 优化，再拿同一批 Case 报 90%，算泛化吗？**

不算。开发集用于诊断，保留集用于检验没有直接针对的任务。按业务场景或来源切分，避免同一文档的近重复泄漏。若当时没有保留集，90%+ 只能叫这组回归 Case 的通过率。

**问：150+ 是总数还是核心 Skills 的分母？**

简历措辞是评测集总规模与核心 Skills 通过率，不一定同一个分母。必须准备确切版本、纳入范围、通过数 / 总数、blocked 是否单列及失败分布。不要从 150 和 90% 推造 135 条通过。

## 这段实习容易被追穿的五个口径

- 「参与 Runtime」：分别说团队已有能力、你的新增改动和后来个人项目的演进。
- 「行业 Agent」：拿一个交付闭环讲，不披露客户身份或受限数据。
- 「20+ Skills」：定义什么算一个，版本和变体是否重复计数。
- 「3 家企业」：内部试点的时间与范围，不等于正式付费或规模上线。
- 「90%+」：哪批 Case、什么规则、谁打分，以及没通过的典型例子。

## 明早 30 分钟闭卷拷打

先花 5 分钟画 Runtime / Role / Skill / Tool。再用 8 分钟模拟两条 IM 消息并发与一次进程重启。用 7 分钟解释一次 Context 压缩错误。最后 10 分钟，拿一个 Skill 从需求讲到上线排障，再报评测的确切分母。

**过关标准**：每个核心模块都能指出一个输入、一个输出、一个失败状态和一份证据；能说出自己没做的边界。暂时说不清的地方写「待核对」，不要用术语填空。
