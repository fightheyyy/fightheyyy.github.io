## 90 秒开场：先说长任务带来的用户问题

用户在飞书里让 Agent 做十分钟浏览器任务，期间仍会补充要求。直接阻塞主会话，交互就停了；让每个子 Agent 自己发消息，又会失去统一交付。你的核心工作是把执行上下文拆开、把结果回到主会话，并让完成状态有据可查。

然后介绍 Jev Router 的具体动机：角色选择不必阻塞主模型的每一步处理。最后只用一句话引出 GauzMem：历史消息不等于可用记忆，检索出的事实还需要来源、关系和时间。

## 一次任务的完整生命周期

```text
IM 输入 → Main 会话
          ├─ 当前对话继续处理
          └─ 路由 / 派生任务 → 独立 SubAgent Session
                                  ↓
                           Tool / Artifact / Trace
                                  ↓
                         完成事件 + 结果摘要
                                  ↓
                     Main 校验归属、组织结果 → IM 交付
```

**问：独立 Session 具体独立在哪里？**

列出各自的历史、工具预算、取消状态、工作目录和 Trace，明确哪些真的隔离、哪些仅是逻辑约束。同进程对象隔离不是操作系统沙箱；不同 session_id 也不会自动阻止文件互相覆盖。

**问：子任务完成时，主会话正好在回复怎么办？**

不能把异步结果随时拼入正在发送给模型的请求。需要解释是否排队为下一条事件、是否使用消息快照，以及新一轮怎样消费它。对同一事件去重，对过期 owner / generation 做检查。若原实现允许竞争，带着最小复现说明已知边界。

**问：任务已取消，结果晚到还能发出去吗？**

先核对当前任务状态与结果归属，再决定保留供查询、丢弃自动交付或标记已过期。已取消不能因为迟到的 success 又变回完成。状态示意可以是 queued → running → succeeded / failed / cancelled；真实命名及转移条件必须按代码讲。

**问：结果写回成功，IM 发送失败怎么办？**

执行完成和交付完成分开。保留产物及发送状态，重试不能重新执行昂贵任务；发送动作还需要避免重复。公开文章使用 Delivery Evidence / External Delivery Receipt 区分证据层次，但不等于平台提供端到端 exactly-once。

## 取消与并发八股：AbortSignal 传到了哪里

**问：`Promise.all` 里一个 reject，其他任务自动停止吗？**

不会。聚合 Promise 的失败不等于取消底层工作。需要由任务所有者传递取消信号并管理清理。`Promise.allSettled` 适合收集独立结果，也不会自动赋予任务正确的生命周期。

**问：AbortController 能杀掉 Python 子进程吗？**

它提供取消信号，是否终止取决于调用方 / Adapter 是否接入。网络请求、浏览器、Shell 和子进程要各自处理；进程树和已发生的远端动作还有额外边界。不能只取消外层 Promise 就声称任务已经停止。[MDN AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController)。

**问：子 Agent 无限派生怎么办？**

检查最大并发、深度、总 Token / 时间预算和取消传播。限制需要在宿主执行，不能只写进 Prompt。你实际没有的限制标作待补，不要把设计检查表当成已完成特性。

**问：为什么 Main 唯一出口？**

统一结果解释、避免多任务刷屏，也让消息归属和交付证据更清楚。代价是主会话可能成为调度与交付瓶颈，需要控制回注内容大小和优先级。原始工具日志不应整段注入主上下文。

## Jev Router：它究竟把哪一步移出了关键路径

**第一层：定义输入输出。**

准备真实的路由输入样例：用户请求、必要上下文和可选角色；输出应是可以校验的路由结果。未知角色、缺参数、置信不足或 Router 超时怎样处理？「让另一个模型决定」还不是完整方案。

**第二层：解释并行。**

画出旧链路 Main 推理 → 角色决策 → 子任务，与新链路主对话 / Router 并行的重叠区。必须说明主回复依赖 Router 的哪些结果；有依赖的步骤不能宣称完全并行。

**第三层：解释重复执行。**

若 Main 和 Router 都判断要执行浏览器任务，谁拥有最终派发权？一个输入对应的路由决定要有唯一归属，派发操作应可去重。否则主模型 Token 少了，却多执行了一次外部副作用。

**第四层：解释回退。**

Router 错选或不可用时，是回到 Main、询问用户、用规则默认角色，还是失败？回退不能默默扩大权限。要用真实异常 Case 说明成本，而不是只讲最好路径。

## 33.1% 与 5.07 秒：面试最可能查的账

| 指标 | 必须说清 | 常见误报 |
| --- | --- | --- |
| Main Token −33.1% | 仅 Main，还是 Router / 子任务都计入？输入、输出、缓存分别怎样算？ | 主模型减少 = 总成本减少 |
| 首次可见回复 12.98s → 5.07s | 首个 ACK、有效文本，还是最终任务结果？ | 首次回应更快 = 完成任务更快 |
| 30 场景、180 次 | 总运行次数？一组 A/B 算一次还是两次？每场景重复几次？ | 自动推导成每场景 3 对或 6 对 |

首次可见回复 P50 下降 7.91 秒，约 60.9%。这个口径和揽岳的首音延迟不同，不能混放在一张「Agent 延迟」对比表里。中位数的比值也不等于每个样本加速比的中位数。

**问：平均 Token 降幅怎么计算？**

「各场景百分比的平均」与「总 Token 加权后的降幅」可能不同。准备原始两列 Token、缺失 / 失败处理及计算脚本。没有脚本时不要临场选一种说法。

**问：路由省了 Token 但任务成功率下降呢？**

同一组运行同时比较任务正确性、路由准确率、总 Token、总耗时和失败类型。对路由确定的任务与需要深推理的任务分层；别只挑提升最大的场景。模型、Prompt、工具环境、并发度和缓存策略要能复述。

**问：180 次足够吗？**

足够观察这批样本中的差异，不自动代表广泛业务。按场景成对比较，报告变异与失败；需要置信区间时可做按场景聚类的重采样，不能把相关的重复运行都视为独立场景。没有做就说后续应补。

**问：Facts 和 Topics 为什么分两层？**

Fact 尽量保留可追溯的原子结论，Topic 聚合长期主题。Topic 帮助定位范围，不能替代原文证据。两层都由模型派生，会有提取和更新误差；面试时拿一个从原文到 Fact 再到 Topic 的真实脱敏样例。

**问：为什么不能只用向量库？**

向量相似适合找到候选，但不天然表示因果、矛盾或事件先后。问题需要「为什么改期」「后来改了吗」时，关系与时间补全有用。若任务只找相似片段，三套存储的复杂度未必划算。

**问：三路是什么？不是三个库各查一次吗？**

公开设计先从语义检索取得 seed Fact IDs，再用这些 ID 扩展图关系和时间邻域，最后合并。后两路与第一路有依赖，不能简单画成完全独立的三路 fan-out。每条召回保留路径与来源，便于解释为什么进入上下文。

**问：MySQL、Neo4j、Qdrant 谁是真相？**

按已有博客，原文、事实及来源关系持久化在 MySQL，向量和图是可重建投影。原文先保存，异步派生失败仍可重试。注意这不自动保证查询时三库一致；需要投影状态、失败重试和可观测性。

**问：用户改口或要求删除怎么办？**

新事实未必应该简单覆盖旧事实；可以保留时间与来源、显式标记冲突或有效期。删除必须覆盖原文、派生事实、图边、向量及缓存的关联范围。本文只是设计追问；实际项目采用何种策略要看代码，不能假设已实现完整删除传播。

**问：多跳越多越好吗？**

不是。扩展会增加噪声、延迟和上下文成本；限定跳数、数量和预算，并保留较短路径。时间轮次必须限制在会话域，跨会话 turn 号没有全局时间语义。跨租户过滤要在检索和扩展两层都保持。

## 86.8%：它不等于整个 XIAOBA 的成功率

这是简历中独立记忆模块在 LoCoMo 上的 LLM Judge 准确率。面试需要补全：数据集版本、纳入哪些题型、样本数、答案提取、Judge 模型与 Prompt、参考答案、随机性和失败处理。

**追问：有没有基线和消融？**

准备只用向量、向量 + 图、向量 + 时间、完整三路的对比，以及相同上下文预算。如果没有做消融，不能把 86.8% 的收益归因于图谱。还要检查测试答案有没有进入记忆、跨对话是否污染、存取时间顺序是否正确。[LoCoMo 原始论文与评测背景](https://arxiv.org/abs/2402.17753)。

**追问：准确率高但慢到不能用呢？**

把写入延迟、后台提取耗时、检索 P50 / P95、上下文长度和调用成本一起看。异步提取意味着刚写入的信息可能还不能从长期索引召回，短期原文与长期记忆要有清晰边界。
