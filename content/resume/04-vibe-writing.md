## 90 秒开场：Java 管什么，Python 管什么

从业务流程讲：用户提供模板与资料 → 解析章节 → 生成计划 → 章节执行 → 审校与合并 → 交付。Java 侧维护业务身份、任务状态和服务边界；Python 侧承载模型与文档处理。这是简历中分层架构的讲述骨架，具体职责按实际实现补齐。

**问：为什么不全用 Python？**

讲已有 Java 业务系统、事务 / 权限或团队维护经验，以及模型生态的差别。不要说 Java 天然负责「高并发」、Python 天然「不能做业务」。两套服务带来的调用失败、版本契约和部署成本也要承认。

## 第一轮：把章节任务拆成可追踪状态

**问：Plan–Execute–Review 各自的输出是什么？**

Plan 应能得到章节结构、依赖和输入约束；Execute 产生章节内容与引用；Review 按规则或语义审查并决定接受、重写或人工处理。必须说清最多重写几次、失败怎样收敛、哪些检查是确定性的。不能用模型说「看起来不错」作为唯一完成判据。

**问：所有章节都能并行吗？**

不一定。共享术语、跨章引用、数据图表和最终结论可能有依赖。先定义共享计划和版本，独立章节再并行，合并时统一审查。12 路是某个工作负载下的能力上界，不代表任何文档都可以分成 12 个完全独立任务。

**问：章节到底何时算成功？**

参考顺序：生成得到内容 → 校验通过 → 产物写入并取得稳定引用 → 条件更新任务状态。发布「成功」之前要说明产物已经可读取。对象存储和数据库不能靠一个本地事务一起原子提交，可能留下孤儿对象或待确认状态，需要可重试的对账。

## 第二轮：RocketMQ 重复投递，怎么不重复写章节

**故障时间线**：消费者已写完产物 → 数据库状态已提交 → ACK 丢失 → 同一消息再次投递。

**参考回答**：消息投递按可能重复来设计，消费端以稳定任务身份查状态并做条件更新。已成功就读取已有结果；执行中需要判定是否仍有效，不能一律吞掉重投。幂等键可包含文档、章节和生成版本；用户主动重生成必须能区分新版本。实际字段需回代码核对。

**追问：加了锁就幂等了吗？**

不是。锁是某段时间的互斥；它释放后同一个消息仍能再来。完成态、版本及唯一性约束才决定重复请求是否再次产生业务效果。写对象存储也要考虑同名覆盖与版本隔离。

**追问：DB 写完但 MQ 发送失败呢？**

这是生产者一侧的双写窗口。参考方案有本地事务 Outbox 加可靠发布，或按 RocketMQ 事务消息机制设计回查；选择取决于当时系统。不能因为消费者幂等就说生产者不会丢任务。若项目当时只做了重试，要说清补偿和对账范围。[RocketMQ 事务消息机制](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)。

**追问：毒消息无限重试怎么办？**

区分网络超时等暂态故障、参数 / 权限等永久失败；限制次数、记录原因、进入可人工处理的失败通道。长任务的业务重试和 Broker 的消息重投不能无意叠成指数级重复调用。不要用重试掩盖系统性错误。

## 第三轮：Redisson Watchdog 保证了什么

**问：为什么长任务不能简单固定 30 秒锁？**

任务可能超过租期，锁过期后第二个执行者进入。Watchdog 在持锁客户端存活且续约正常时延长有效期。但它不能保证所有暂停和网络分区中锁永远不丢，也不能阻止失去所有权的旧任务继续外部写入。[Redisson 锁与续约说明](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/)。

**问：显式指定 leaseTime 和自动续约是什么关系？**

要按项目使用的 Redisson 版本和调用重载核对；不能声称任何 `lock()` 调用都会得到完全相同的续约行为。准备真实代码一行，说明等待时间、租约和锁所有者线程的含义。

**问：锁粒度是什么？**

文档级锁可能把所有章节串行化；章节版本级锁能避免同一章节重复执行，却无法单独限制整个系统只有 12 路并发。全局上限、单租户配额和任务去重是不同约束。你必须指出 12 路由消费者并发、工作池、信号量还是其他机制实现；简历没有写，不能猜。

**问：锁过期后旧任务回来怎么办？**

需要结果提交时再校验当前执行版本 / owner；有单调 fencing token 时由资源端拒绝旧 token。仅客户端认为自己持锁不够。若原实现只有锁与任务状态，重点检查状态条件是否能拒绝旧结果，并坦诚未覆盖的窗口。[Redis 分布式锁的安全边界](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。

## 第四轮：Spring、MySQL 的八股怎么贴到项目上

**问：远程模型调用要放进数据库事务吗？**

通常不应持有数据库事务等待数十秒模型调用：会拉长锁持有与连接占用。短事务负责登记 / 认领，外部执行后用短事务条件提交。业务流程的一致性不能靠把整个流程塞进一个 `@Transactional` 得到。

**问：`@Transactional` 为什么不生效？**

默认代理模式下，同类内部调用不会经过代理；还要核对代理对象、方法可见性、事务管理器及异常规则。异常被捕获后不再抛出，或不同线程执行，都可能与直觉不同。用你实际服务方法解释，别只背「自调用失效」。[Spring 声明式事务注解](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)。

**问：如何避免两个 Worker 都把任务从 queued 改为 running？**

可以讨论带旧状态 / version 条件的更新，并检查受影响行数；唯一约束用于防重复业务身份。隔离级别不是幂等性的替代品。下面只表示 compare-and-set 语义，不是可直接复制的项目 SQL：

```sql
UPDATE chapter_task
SET status = 'running', version = version + 1
WHERE id = :id AND status = 'queued' AND version = :expected_version;
-- 只有 affected_rows = 1 的执行者认领成功。
```

**问：任务查询索引怎样设计？**

从实际查询条件和排序开始，例如租户、文档、状态、更新时间，而不是把每个字段都建索引。用 EXPLAIN 和数据分布验证；区分唯一约束、加速查询和锁扫描范围。没有任务表规模或执行计划，就不要报毫秒级性能。

## 第五轮：Redis + SSE，断线以后进度从哪里来

**问：为什么用 SSE，而不是 WebSocket？**

生成进度主要是服务端单向推送，SSE 的协议和浏览器支持适合这个方向。停止 / 重试可以继续走普通 HTTP。需要双向高频交互才有另一套取舍；别说 SSE 在所有条件下更快。

**问：Redis Pub/Sub 是持久进度队列吗？**

不是，订阅者离线时可能错过事件。参考设计是数据库提供状态快照，推送作为通知；需要事件回放时使用有历史的事件存储 / Stream 等机制。简历写 Redis，不代表一定用了 Stream。先核对实际实现。

**问：客户端重连怎样不倒退？**

服务端事件带任务身份和单调序号；客户端拉最新快照，再按游标接续或忽略过期事件。SSE 的 `id` / `Last-Event-ID` 需要服务端配合历史存储，不会自动帮你保存事件。还要检查代理缓冲、心跳、连接清理和鉴权。[MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。

**问：12 章的进度按百分比平均靠谱吗？**

章节耗时和工作量不同。可以提供已完成章节数及当前阶段，避免伪造精确的剩余时间。最终完成以持久任务状态为准，不能仅因前端计数到 100% 就显示可下载。

## 第六轮：混合检索不是堆组件

**问：BM25、向量各自漏什么？**

BM25 擅长词项与编号等字面命中，可能漏同义表述；向量擅长语义相关，可能混淆相近但不同的型号、数字或否定关系。拿一个业务 Query 展示两边结果，而不是只讲概念。

**问：为什么不用分数直接相加？**

不同检索器的分数尺度不统一。RRF 根据排名融合，典型形式是对各路的 `1 / (k + rank)` 求和，再选候选。它解决融合，不负责最终语义判定；Reranker 再对较小候选集做精排。本文描述算法，不代表项目一定使用了 Elasticsearch 自带 RRF API。[Elastic RRF 说明](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)。

**问：文档解析、切片和引用怎么连起来？**

MinerU 的解析结果需要保留文档、页码、段落或块的来源，表格和图片也要有引用身份。切片不能随意切断标题与表格语义；重排后仍要保留 source IDs。模型生成了引用标记不代表原文支持结论，需要证据校验。

**问：30% 是什么？**

必须补指标名称：Recall@K、命中率、MRR、nDCG，还是人工问答准确率？是绝对百分点还是相对增长？例如 50% → 65% 是相对 +30%，绝对 +15 个百分点，这只是算术例子，不是你的结果。应给出固定查询集、标注集、基线、K、权限过滤和失败样例。

## 「万字低于 4 分钟」的条件合同

准备文档类型、字数计算、图文数量、模型与硬件、并发限制、资料规模、是否包含解析 / 排队 / 重试，以及报告是否经过审校。最高 12 路和低于 4 分钟未必来自同一轮测试，除非你能拿出对应记录。

还有一个经常被忽视的追问：并行写得更快，内容是否更矛盾？用术语一致、跨章引用、数字一致和重复段落检查回答，而不是只报耗时。

## 明早 30 分钟闭卷拷打

用 10 分钟给「创建任务 → MQ → Worker → 产物 → 完成状态 → SSE」的每个间隙注入一次崩溃。再用 8 分钟解释锁、幂等、全局限流三者区别。用 7 分钟讲 BM25 到引用的全过程，最后 5 分钟解释四分钟和 30% 的口径。

**待补证据**：章节任务真实状态表、锁调用及粒度、消息重投测试、SSE 重连行为、生成计时记录、检索评测表与奖项个人贡献说明。优先核对这些，不额外扩展框架。
